# IoTmx REST API Project

In this project we are going to work on improving a Python app that implements an IoT platform focused on providing services. The idea is to be able to offer a variety of services such as fleet tracking, process monitoring, remote equipment control (not real-time), etc., all from a single platform.

## High-Level Design
### Ecosystem elements:
1. master admin: can access the entire ecosystem without restriction; it is the same entity that deploys the ecosystem and has access to the infrastructure. The master admin is the only one who can create "regular" admins.
2. admin: can perform management tasks for the IoT ecosystem and its infrastructure (DBs, APIs). They are responsible for creating services, registering devices, users, applications, managers, handling tickets, etc.
3. managers: responsible for managing the services, as well as their linked devices and users.
4. users: the entities that generate and consume information within the ecosystem; they must always be linked to a service.
5. applications: the web or mobile applications that have permission to communicate with the ecosystem. These applications can be the frontends that users see for interacting with the system.
6. devices: the IoT devices that operate remotely; they belong to the ecosystem and are assigned to a service and a user.
7. services: the specific services provided to end clients.

### Architecture characteristics:
1. The structure of the IoT ecosystem (elements, characteristics, hierarchies, applications, devices, services, tickets, billing) is captured in a relational DB.
2. The variability in the ecosystem's applications is handled by using a non-relational DB for the data generated by devices or by elements within a service inside the ecosystem.
4. There are entities linked directly to the ecosystem and others that are linked to services.
5. The architecture integrates authentication mechanisms in a modular way to provide crypto-agility.
6. Each entity has a table in the DB; users within services are distinguished by role.
7. The structure is established to be able to manage payments for the services.


### Security characteristics:
1. Different authentication mechanisms are integrated and can be chosen based on the entity and its capabilities.
2. Human users will use some 2FA-based mechanism.
3. Devices may use other key-based methods.
4. A Root of Trust process (RoTP) is defined, where each entity must generate and share the cryptographic parameters used during the authentication mechanisms.
5. After the RoTP, all communications between entities will be encrypted using AES-265, using key-exchange mechanisms.

### Desired characteristics:
1. The ecosystem requires more types of entities in order to provide technical support, not just admins; define entity types.
2. Payments should enable the service, and the lack of payments should disable the service, for the user in question.
3. Services must be able to run as part of the server or as a fully independent service from the server.
4. This platform must provide service to different clients with complex and variable organizational structures.

        entity = self.repository.get_by_id(id)
        if not entity:

    def get_all(self, offset: int = 0, limit: int = 20) -> PageResponse[T]:
        items, total = self.repository.get_all(offset, limit)
        return PageResponse(total=total, offset=offset, limit=limit, data=items)

        entity = self.repository.create(self._build_entity(payload))
        self._log_audit("create", entity)

        old = entity.model_dump()

        self._log_audit("update", entity, old)

        self.repository.delete(entity)

    def _log_audit(self, action: str, entity: T, old: dict | None = None) -> None:

            account_type=current_user.account_type,
            action=action,
            resource_type=self.entity_name,
            resource_id=entity.id,
